## 1. 概要

クライアントが「短い招待コード8文字」と「パスワード」を入力するとギャラリーが開く入口を作る。
現在の21文字のトークン付きリンクは**そのまま残す**。コード入力はリンクが使えない場面の代替であり、
置き換えではない。

## 2. 目的

- **利用者の目的**: メールや LINE のアプリ内ブラウザにリンクを横取りされたとき、
  口頭やチラシで伝えられる短い文字列からギャラリーへ到達できる。
- **事業上の目的**: 撮影現場でコードとパスワードを紙で渡せる。

## 4. スコープ

- 招待に**招待コード8文字**と**パスワード**を持たせる
- 管理画面の招待作成でコードを自動生成し、パスワードを設定できるようにする
- web に `POST /api/invitation/open`（コード＋パスワード → トークン）を作る
- web のトップページをコード入力フォームにする
- アプリの貼り付け画面にパスワード欄を足す
- 総当たり対策（招待単位のロック＋発信元単位のレート制限）

## 5. スコープ外

- 既存のトークン付きリンクの廃止（**残す**）
- クライアント自身によるパスワード変更（管理者が再設定する）
- 「案件名」での検索（**採用しない**。§6-2）
- CAPTCHA / Turnstile（レート制限で足りなければ次の段階で検討する）

## 6. 前提

1. **コード＋パスワードの経路は、リンク経路より本質的に弱い。** 21文字のトークンは実質推測不能だが、
   8文字のコードと人が決めるパスワードは総当たりの対象になる。
   **試行回数の制限が無いならこの機能を入れてはいけない。**
2. **「案件名」は使わない。** 「田中様 結婚式」は推測できる。1要素目は推測不能でなければ意味がない。
3. **照合はサーバー側でしかできない。** Firestore のルールはクライアントが送った任意の文字列を
   `get` の条件に使えず、ハッシュ計算もできない。コードから招待を引くには `list` が要るが、
   それは塞いだ穴そのものである。
4. パスワードは**平文で保存しない**。`node:crypto` の**非同期** `scrypt` を使う（依存を増やさない）。
5. Route Handler は `runtime = 'nodejs'`。Edge では `node:crypto` の `scrypt` も `firebase-admin` も動かない。

## 7. アーキテクチャへの影響

### 7.1 なぜ Admin SDK を入れるのか

`web/src/lib/firebaseServer.ts` は「サービスアカウント鍵を運用に持ち込まずに済む利点を採った」と
書いてある。今回はその判断を**覆す**。

1. コードから招待を引くには `list` が要る。クライアント SDK ではルールに縛られるため、
   `list` を匿名に開放することになる。それは塞いだ穴を開け直すことである。
2. パスワードハッシュをクライアントに読ませると、オフラインでの総当たりを許す。
3. 試行回数のカウンタをクライアントに書かせると、クライアントが消せる。

**運用条件**（v1 で漏れていた）:
- 専用のサービスアカウントを作り、Firestore への最小権限だけを与える
- Vercel の環境変数は **Sensitive** にする。`NEXT_PUBLIC_` を付けない
- private key の改行の扱いをローカルと Vercel の両方で実際に確認する
- Preview 環境と Production 環境で鍵を分ける
- 鍵はリポジトリにコミットしない

### 7.2 採用しなかった案

**ハッシュをドキュメント ID にする案**（`codeLookups/{sha256(code + ':' + password)}` に token を置き、
クライアントが単一取得する）。Admin SDK が不要な点は良いが、**試行回数を制限できない**。
攻撃者は Firestore に直接 `get` を投げ続けられ、こちらに止める手段がない。

### 7.3 Firestore の構成

**ドキュメント ID はトークンのまま変えない。** 既存のリンク経路を壊さないため。

| コレクション | ID | 中身 | ルール |
| --- | --- | --- | --- |
| `invitations/{token}` | トークン | 現状のまま。**秘密は入れない** | 現状のまま |
| `invitationCodes/{code}` | 招待コード（正規化済み） | `{ token }` | `allow read, write: if false` |
| `invitationSecrets/{token}` | トークン | `passwordHash` / `failedAttempts` / `lockedUntil` | `allow read, write: if false` |

**秘密を `invitations` に相乗りさせない。** Firestore は**フィールド単位の読み取り制御ができない**。
同じドキュメントに置くと、トークンを知っている正規の閲覧者が他人のパスワードハッシュを読める。

**`invitationCodes` を別に持つ理由は3つある。**
1. コードの一意性を、`create()` の衝突で Firestore に保証させられる（確認してから書くと競合に負ける）
2. 引くのが ID 指定の `get` になる。`where('code','==')` より速く、**ヒットの有無で時間が変わりにくい**
3. コードを変えても `invitations` を触らずに済む

### 7.4 コードの形式

アルファベットは `ABCDEFGHJKMNPQRSTVWXYZ23456789` の **30文字**。`I` `L` `O` `U` を除いてある
（`1/I/L`、`0/O`、`U/V` の取り違えを避ける。**`V` は残す**）。8文字で **30^8 ≒ 6,561億通り**。
表示は `ABCD-EFGH`。照合時はハイフンと空白を除去し大文字化する。

### 7.5 総当たり対策

**2層で守る。片方だけでは足りない。**

**(a) 招待単位のロック**（`invitationSecrets` に持つ、トランザクションで更新）

| 段階 | 挙動 |
| --- | --- |
| 失敗 5 回 | 1分ロック |
| 失敗 10 回 | 15分ロック |
| 失敗 20 回 | 24時間ロック |

**`failedAttempts` の読み取り・判定・更新は必ずトランザクションで行う。**
並行リクエストが同じ値を読んで上書きすると、5回失敗しても1回扱いになりロックが効かない。

**(b) 発信元単位のレート制限**（v1 で「しない」と書いたが、必要）

理由は2つある。
1. **scrypt を毎回実行する設計は、そのままだと CPU を消費させる的になる。**
   存在しないコードを投げ続けるだけで、こちらの計算資源と請求が増える
2. 招待単位のロックは、存在しないコードには効かない（カウント先のドキュメントが無い）

制限は**高コストな処理（scrypt と Firestore アクセス）の前**に置く。
超過時は一律 429 を返す（この経路では存在の有無を判定しないので漏洩しない）。

### 7.6 存在の有無を漏らさない

**v1 の最大の穴はここだった。** 401 の本文を揃えても、**423 が返るのは実在するコードだけ**なので、
候補コードに6回失敗を投げて 423 が返るかどうかで存在が分かる。

対策:
- **存在しないコードにも失敗カウンタを持たせる。** `invitationCodes` に無いコードは
  `unknownCodeAttempts/{sha256(normalizedCode)}` に記録し、同じ段階で 423 を返す
- 401 と 423 の**本文と `retryAfterSeconds` の出し方を、存在・非存在で同一**にする
- **応答時間を揃える**: 非存在でも scrypt をダミーのハッシュに対して実行し、
  さらに全経路で**最低応答時間**（例: 300ms）を満たすまで待ってから返す
  （Firestore の I/O 回数の差は scrypt だけでは埋まらない）

これでも漏洩が完全にゼロにはならない。**残留リスクとして受け入れる**ことをここに明記しておく。

## 8. API

### `POST /api/invitation/open`

```
Request:  { "code": "ABCD-EFGH", "password": "..." }
Response: 200 { "token": "<21文字>" }
          401 { "error": "invalid" }                       // コード違い・パスワード違い・存在しない・期限切れ（すべて区別しない）
          423 { "error": "locked", "retryAfterSeconds": N } // 存在・非存在で同じ条件で返す
          429 { "error": "too_many_requests" }             // 発信元単位の制限
          400 { "error": "bad_request" }                   // 形式不正
```

- `export const runtime = 'nodejs'`
- `Cache-Control: no-store`。**Route Handler は既定でキャッシュされず POST もキャッシュされないが、
  中間キャッシュへの多層防御として明示する**（v1 の「付けないと CDN に載る」は誤り）
- **パスワードの最大長を先に制限する**（例: 128文字）。制限しないと scrypt の入力で殴られる
- 成功時に `failedAttempts` を 0 に戻し、`lockedUntil` を消す（同じトランザクション内）
- 成功後、招待が `isActive` かつ `expiresAt > now` であることも確認する。
  **期限切れの招待のトークンを渡さない。** 失敗時の応答は 401 で他と同一

## 9. UI

### web `/`（`web/src/app/page.tsx`）

現在の静的ページをフォームに置き換える。コード欄・パスワード欄・「開く」ボタン。
成功したら `/gallery/<token>` へ遷移する。日英併記にする。

**正規化関数（`normalizeCode` / `formatCode`）はクライアントでも使う。**
`node:crypto` を使うハッシュ関数とは**別モジュール**に置き、サーバー専用側には `server-only` を付ける。
同居させるとクライアントバンドルに `node:crypto` が引き込まれてビルドが壊れる。

### アプリ `OpenByLinkScreen`

既存の1入力にパスワード欄を足す。判定は**3分岐**にする。

| 入力 | 扱い |
| --- | --- |
| スキーム付き（`https://...` / `photogallery://...`） | 今のまま `resolveDeepLink` へ。パスワード不要 |
| **21文字で `TOKEN_ALPHABET` のみ** | **今のままトークンとして** `/gallery/<token>` を組み立てる。パスワード不要 |
| 8文字でコードのアルファベットのみ | パスワード必須。`/api/invitation/open` を叩く |
| それ以外 | エラー |

**21文字の分岐を落とすと既存の「トークンだけ貼り付け」が壊れる。**
`mobile/src/navigation/resolveInitialUrl.test.ts` は21文字トークンの貼り付けを検証している。

### 管理画面 招待作成

- コードは自動生成して表示する（編集不可）
- パスワードは**サーバーで生成した候補**を既定にする。管理者が書き換える場合は
  **最低12文字・よくあるパスワードの拒否リスト**を課す
- **作成後はパスワードを二度と表示しない**（ハッシュしか保存しない）。その旨を画面に明示し、コピーボタンを置く
- 招待詳細に「パスワードを再設定」を置く（再設定でロックも解除する）

**admin から `invitationSecrets` は書けない**（ルールで閉じており、admin はクライアント SDK）。
認可はこう決める（v1 では先送りしていた）:

1. admin のブラウザが Firebase の **ID トークン**を取得し、`Authorization: Bearer <token>` で送る
2. サーバー側で Admin SDK の `verifyIdToken()` で検証する
3. デコードした uid で `users/{uid}` を読み、`role == 'admin'` を確認する
4. 通った場合だけ `invitationSecrets` / `invitationCodes` に書く

**`users/{uid}` の role をクライアントが書けないことが前提**である（2026-08-22 に修正済み）。

2. エラー出力をそのまま記録する
3. エラーを task_id に対応付ける

**テストを通すためにテストを緩めない。**

今いるクライアントがギャラリーを開けなくなる。各タスクでリンク経路の回帰を確認する。
