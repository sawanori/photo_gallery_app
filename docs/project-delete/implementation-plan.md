## 1. Overview

管理画面からプロジェクトを削除すると、完了までに数分かかる。
画像を1枚ずつ直列に消しており、1枚あたり8〜11回のサーバー往復が発生しているためである。
あわせて、Firestore のトランザクションの中で Storage の削除とお気に入りの検索を
行っているという設計上の誤りがある。

削除の**所要時間を短縮**し、**トランザクションの誤用を正す**。

## 2. Goal

**利用者の目的**: 不要になったプロジェクトを、待たされずに削除できる。

**事業上の目的**: 納品が終わった案件を整理できるようにする。
Firebase Storage の無料枠は 5GB で、原本が1枚3〜4MB あるため
**1案件700枚で約2.5GB を占める**。削除が現実的な時間で終わらないと、
storage の課金が積み上がる。

## 3. Current State

### 削除の経路

`admin/src/services/projectService.ts` の `deleteProject` が次を行う。

```
画像を取得 → for ループで1枚ずつ await deleteImage()
招待を取得 → for ループで1件ずつ await deleteInvitation()
プロジェクトのドキュメントを削除
```

**画像も招待も直列である。** 既に `deleteImages`（`Promise.all` による並列版）が
`imageService.ts` に存在するが、`deleteProject` はそれを使わず自前の直列ループを持っている。

### 画像1枚あたりの往復回数

`deleteImage`（`admin/src/services/imageService.ts`）の内訳。

| 処理 | 往復 |
|---|---|
| トランザクション内での画像ドキュメント読み取り | 1 |
| 原本を Storage から削除 | 1 |
| サムネイル2枚を Storage から削除 | 2 |
| お気に入りの検索（`where('imageId','==',id)`） | 1 |
| 見つかったお気に入りを1件ずつ削除 | 件数分 |
| トランザクションのコミット（画像削除＋`imageCount` の更新） | 1 |
| `syncInvitationsOnImageDelete` の招待取得 | 1 |
| 各招待への `arrayRemove` | 招待数 |
| **合計（招待3件・お気に入り0件の場合）** | **約10** |

**700枚なら約7,000回の往復**になる。1回100ミリ秒としても十数分に達する。

### トランザクションの誤用（設計上の誤り）

`deleteImage` は `runTransaction` の中で次を行っている。

- `deleteObject`（Storage からの削除）
- `getDocs`（お気に入りの検索）
- `deleteDoc`（お気に入りの削除）

**Firestore のトランザクションは競合時に自動で再実行される。**
再実行のたびに Storage の削除とお気に入りの削除も繰り返される。
処理が重いほど競合しやすく、競合するほど遅くなる。
トランザクションには時間制限もあり、超えると失敗する。

コード中のコメントには
`// Delete associated likes (best-effort, outside transaction)` とあるが、
**実際にはトランザクションの中にある。** 意図と実装がずれている。

### プロジェクトごと削除するときの無駄

- `imageCount` を1枚ずつ `increment(-1)` している。**プロジェクト自体を消すので不要**
- `syncInvitationsOnImageDelete` が1枚ごとに招待を取得し `arrayRemove` している。
  **招待も同時に消すので不要**。しかも**招待の取得が画像の枚数分**繰り返される

### 呼び出し元

| 場所 | 呼び方 |
|---|---|
| `admin/.../projects/[projectId]/page.tsx:102` | 1件を削除 |
| `admin/.../dashboard/page.tsx:60` | 期限切れを `Promise.all` で複数同時に削除 |
| `admin/.../dashboard/page.tsx:81` | 1件を削除 |

**ダッシュボードの一括削除は、プロジェクト間では並列だがプロジェクト内は直列**である。

### UI

`modal.confirm` で確認したあと `await deleteProject(projectId)` するだけで、
**進捗表示が無い**。数分待つ間、利用者には何も見えない。

### 未計測

**所要時間を実測していない。** 上記の往復回数はコードから数えた値である。
実測は `task_001` で行う。

## 4. Scope

- **`firestore.rules` の `likes` に管理者の削除権限を追加する**（これが無いと削除が成立しない）
- `deleteProject` を、プロジェクトごと消すことに最適化した経路に変える
- `deleteImage` のトランザクション誤用を正す（Storage とお気に入りを外に出す）
- 画像・招待の削除を並列化し、Firestore の一括書き込みを使う
- 削除の進捗を UI に出す
- 改善の前後を実測して記録する

## 5. Non-Scope

- **画像1枚の削除（`deleteImage`）の呼び出し側の仕様変更**。
  画面から1枚削除する経路では `imageCount` の更新と招待同期が必要であり、
  そこは維持する
- **Cloud Functions への移行**。サーバー側で削除するほうが速いが、
  Functions を導入していないため、この修正の範囲を超える
- Storage のライフサイクル設定による自動削除
- 削除の取り消し（ゴミ箱）機能
- `deleteInvitation` の実装変更
- 他のコレクション（`sessions` など）の掃除
- **`storage.rules` の管理者削除権限の追加**。現在アップロードしている管理者は1名で
  実害が無く、ルール変更は影響範囲が広い。`task_007` に記録する

## 6. Assumptions

1. **プロジェクト削除では招待同期を行わない。招待そのものを最初に消すため。**
   ただし **`imageCount` はバッチごとに減算する**（初版から変更）。
   省くと、部分失敗時に「700枚」と表示されたまま中身が空のプロジェクトが残り、
   管理者が状態を判断できなくなる。減算は500件につき1回で、性能への影響は無視できる。

2. **Storage の削除は best-effort のままとする。**
   ただし**画像ドキュメントより先に消す**（初版から変更）。
   後に回すと、失敗したときに `storagePath` を失い、数GBのファイルが永久に孤児になる。
   先に消せば「ドキュメントはあるがファイルが無い」状態で止まり、再実行で回復できる。

3. **必須の削除（Firestore のドキュメント）が1件でも失敗したら中断する。**
   `runWithConcurrency` は「1件が失敗しても全体を止めない」と明記された設計であり、
   そのまま使うと失敗を握りつぶしてプロジェクトのドキュメントまで消してしまう。
   結果を集計し、失敗があれば例外にする。**Storage だけを best-effort にする。**

4. **同時実行数は 4 を起点とする（初版の 20 は根拠が無かった）。**
   実在の前例はアップロード画面の `UPLOAD_CONCURRENCY = 4` である。
   削除はアップロードより軽いため増やせる可能性があるが、
   **`task_006` で実測してから決める**。
   あわせて**ダッシュボードの一括削除はプロジェクトを直列にする**。
   現在は `Promise.all` で並列に呼んでおり、同時実行数がプロジェクト数倍に膨らむ。

5. **Firestore の一括書き込みは1回あたり最大500「操作」**である（初版は「件数」と誤記）。
   画像・お気に入り・招待を同じバッチに積むと合算されるため、操作数で数える。

6. **既存のデータに対する移行は不要。** 削除処理の変更であり、
   保存されているデータの形は変えない。
   ただし**既に溜まっている孤児のお気に入り**（管理者が削除できなかった分）は残る。
   掃除は `task_007` の任意タスクで扱う。

7. **`getImagesByProject` は件数の上限を持たない。**
   数千枚のプロジェクトでも全件を一度に取得する。今回は変更しないが、
   極端に大きなプロジェクトでは取得自体が重くなりうることを記録しておく。

## 7. Architecture Impact

**フロントエンド（admin）**: 削除の進捗を表示する。サービス層の関数の形が変わる。

**バックエンド**: 変更なし。

**データベース**: スキーマの変更なし。書き込みの方法（1件ずつ → 一括）が変わる。

**Firestore ルールの変更が必要である（初版の「不要」は誤り）。**
`likes` の削除ルールに `isAdmin()` が無く、**管理者はお気に入りを削除できない**。

```
allow delete: if hasValidSession() &&
  resource.data.invitationId == sessionInvitationId();
```

2026-08-17 にお気に入りを招待単位へ変更した際に管理者の経路が落ちた。
現在 `deleteImage` の `try-catch` が握りつぶしているため表面化していないが、
**画像を削除してもお気に入りは消えずに溜まり続けている。**
`writeBatch` に含めると、1件の権限エラーで**バッチ全体が巻き戻り、削除が永久に失敗する**。

**ストレージ**: 削除の呼び出し方が変わる（直列 → 並列）。削除するファイルは同じ。

**既知の制約（今回は直さない）**: `storage.rules` の削除は
`request.auth.uid == userId`（アップロードした本人）に限られる。
別の管理者がアップロードした写真は Storage から削除できない。
現在アップロードしているのは `snp.inc.info@gmail.com`（uid `6IK2lVyc…`）の1名のみで
実害は出ていないが、管理者が増えると孤児が生じる。`task_007` に任意タスクとして記録する。

**インフラ**: 変更なし。

## 8. UI Plan

### 削除中の進捗表示

現在は `modal.confirm` の `onOk` が終わるまで何も出ない。
Ant Design の `message.loading` を使い、進捗を更新する。

- 開始時: 「削除しています… 0 / 700」
- 進行中: 完了した枚数で更新する
- 完了時: 「プロジェクトを削除しました」
- 失敗時: 「プロジェクトの削除に失敗しました」（既存の文言を維持）

**キャンセルは提供しない。** 途中で止めると、画像が半分消えたプロジェクトが残る。
削除は確認ダイアログを経ており、取り消せないことは既に伝えている。

### ダッシュボードの一括削除

`Promise.all` で複数のプロジェクトを同時に削除している。
**進捗はプロジェクト単位で出す**（「3 / 5 件のプロジェクトを削除しました」）。
プロジェクト内の枚数まで出すと表示が煩雑になる。

## 9. API Plan

**新しいエンドポイントは追加しない。** 管理画面から Firestore と Storage を直接操作する
現在の構成を維持する。

## 10. Database Plan

**スキーマの変更なし。インデックスの追加なし。**

書き込みの方法が変わる。

| 対象 | 現在 | 変更後 |
|---|---|---|
| 画像ドキュメント | 1件ずつ `transaction.delete` | `writeBatch` で最大500件ずつ |
| お気に入り | 画像ごとに検索して1件ずつ削除 | 画像ごとに検索し、`writeBatch` でまとめて削除 |
| 招待 | 1件ずつ `deleteDoc` | `writeBatch` でまとめて削除 |
| `imageCount` | 1枚ごとに `increment(-1)` | **バッチごとに `increment(-件数)`**（部分失敗時に表示と実態がずれないため） |

**`writeBatch` はこのリポジトリで未使用**である。初めて導入する。
テスト用のモック（`admin/src/test/mocks/firebase.ts`）にも `writeBatch` が無いため追加する。

**上限500は「ドキュメント数」ではなく「操作数」**である（初版の誤り）。
画像・お気に入り・招待を同じバッチに積むと合算される。操作数を数えるチャンカーを作る。

## 12. Implementation Order

1. `task_001` 変更前の所要時間を実測して記録する
2. `task_002` **管理者がお気に入りを削除できるようにルールを直す**（これが無いと以降が成立しない）
3. `task_003` `deleteImage` のトランザクション誤用と削除順序を正す
4. `task_004` プロジェクト削除用の一括削除経路を作る
5. `task_005` 削除の進捗を UI に出す
6. `task_006` 変更後を実測し、同時実行数を調整する
7. `task_007` [任意] 孤児になったデータ（お気に入り・Storage のファイル）を掃除する

### 削除の順序（初版から変更）

```
1. 招待を消す        ← 最初。アクセスを断つ
2. Storage を消す    ← storagePath を失う前に
3. 画像ドキュメントを消す（imageCount も減らす）
4. プロジェクトを消す ← 最後。失敗しても再実行できる
```

**招待を最初に消す理由**: 画像を先に消して途中で失敗すると、
**生きた招待リンクが壊れたギャラリーを指したまま残る**。
クライアントが「写真が消えた」画面を見ることになる。

**Storage を画像ドキュメントより先に消す理由**: 逆にすると、
失敗したときに**どのファイルを消すべきかの情報（`storagePath`）が失われ**、
数GBのファイルが永久に孤児になる。この順序なら再実行で回復できる。
代償として「ドキュメントはあるがファイルが無い」状態が一時的に生じうるが、
それは画面上で壊れた画像として見え、再実行で解消する。

## 13. Verification Commands

リポジトリに実在し、実際に検査が動くものだけを挙げる。

```
cd admin && npx vitest run
cd admin && npx eslint src
cd admin && npm run build
```

**`cd admin && npm run lint` は使わない。** `package.json` の lint は `next lint` だが、
新しい Next.js では `next lint` が廃止されており、`lint` がディレクトリ名として解釈される。
エラーメッセージを出しながら**終了コード 0 を返す**ため、通っても何も保証しない。

現在のベースライン: `npx eslint src` は 0 errors / 1 warning。
`npx vitest run` は 146 tests。

## 14. Acceptance Criteria

1. 700枚規模のプロジェクトの削除が、**変更前の所要時間の 1/5 以下**になる
   （具体的な秒数は `task_001` の実測後に確定する）
0. **管理者が画像を削除すると、その画像のお気に入りも実際に消える**（現在は消えていない）
2. 削除後、プロジェクト・画像ドキュメント・招待がすべて消えている
3. 削除後、Storage の原本とサムネイルが消えている（best-effort のため一部残る場合はログに出る）
4. 削除中、利用者に進捗が見える
5. **`runTransaction` の中に Storage の操作とお気に入りの検索が無い**
6. 画面から画像を1枚だけ削除する経路が、従来どおり `imageCount` を更新し招待を同期する（回帰）
7. 途中で失敗しても、プロジェクトのドキュメントが消えずに残る（画像だけ消えた状態を検知できる）
8. 必須の削除（Firestore のドキュメント）が失敗した場合、プロジェクトのドキュメントを消さずに中断する
9. ダッシュボードの一括削除で、同時実行数がプロジェクト数倍に膨らまない
10. 検証コマンドが既存のベースラインを超えない

## 15. Repair Loop

1. 検証コマンドを実行する
2. エラー出力をそのまま記録する
3. エラーを task_id に対応付ける
4. 関係するファイルだけを修正する
5. 検証コマンドを再実行する
6. 実装が計画と食い違ったら、この計画書を更新してから進める

**テストを通すためにテストを緩めない。**

**削除は取り消せない。** 実データで試す前に、必ず捨ててよいプロジェクトを作って試すこと。
`task_001` と `task_006` の実測は、**専用に作った使い捨てのプロジェクト**で行う。

**「速くなったはず」で終わらせない。** `docs/admin-upload/measurement.md` は
アップロード改善の実測を残せないまま「未計測」で終わっている。同じことを繰り返さない。
