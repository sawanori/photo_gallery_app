## 変更前の実測（2026-08-22）

**計測の経緯**: 利用者が本番（デプロイ済み＝変更前のコード）の admin で
48枚の test プロジェクトを削除している最中に、外部から Firestore を読んで観測した。
意図した計測ではないが、変更前の実データである。

**観測方法**: 招待ドキュメントの `imageIds` の長さを20秒間隔で読む。
変更前の `deleteImage` は画像1枚ごとに `syncInvitationsOnImageDelete` を呼び、
`arrayRemove` で招待から画像 ID を1件ずつ外す。この減り方がそのまま進捗になる。

```
+  0秒  imageIds  36 件
+ 20秒  imageIds  36 件
+ 40秒  imageIds  35 件
+ 60秒  imageIds  35 件
+ 80秒  imageIds  35 件
+100秒  imageIds  34 件
+120秒  imageIds  34 件
+141秒  imageIds  34 件
```

| 項目 | 値 |
| --- | --- |
| 速度 | **約70秒 / 枚**（141秒で2枚。標本は小さい） |
| 48枚の見込み | 約56分 |
| 700枚の見込み | 約13.6時間 |

**この遅さは往復回数だけでは説明がつかない。** 1枚あたり9往復で、
asia-northeast1 への往復が仮に50msでも0.5秒程度にしかならない。70秒はその140倍である。

もっとも疑わしいのは、変更前の `deleteImage` が **`runTransaction` のコールバックの中で
`deleteObject`（Storage）と `getDocs`（お気に入り検索）を待っている**ことである。
トランザクションは競合や失敗で**丸ごと再実行**され、そのたびに Storage の削除もやり直される。
再実行にはバックオフが入るため、1枚あたりの時間が指数的に伸びうる。

`task_003` でトランザクションの外に出した変更は、この構造そのものを消している。

**未計測**: 変更後の所要時間。同じ条件（48枚）で測って比較すること。

## 変更前の往復回数（700枚・招待2件・お気に入り0件の場合）

`deleteProject` は画像を1枚ずつ**直列**に処理していた。1枚あたりの内訳:

| 処理 | 往復 |
| --- | --- |
| `runTransaction` 内の `transaction.get(image)` | 1 |
| Storage: 原本の削除 | 1 |
| Storage: サムネイル2枚の削除 | 2 |
| `getDocs(likes where imageId == ...)` | 1 |
| `deleteDoc(like)` × お気に入り件数 | 0 |
| トランザクションの commit（画像削除 + imageCount 更新） | 1 |
| `getInvitationsByProject`（**画像1枚ごとに毎回**） | 1 |
| `updateDoc(invitation)` × 招待件数 | 2 |

1枚あたり **9往復**、これが700枚分**直列**に積み上がる = **6,300往復**。
うち Firestore が 700 × 6 = 4,200、Storage が 700 × 3 = 2,100。

## 変更後の往復回数（同条件）

| 処理 | 往復 |
| --- | --- |
| `getInvitationsByProject` | 1 |
| 招待の一括削除（writeBatch 1回） | 1 |
| `getImagesByProject` | 1 |
| お気に入りの検索（`in` で30件ずつ = 24クエリ、4並列） | 24 |
| Storage の削除（700 × 3 = 2,100、4並列） | 2,100 |
| 画像とお気に入りの一括削除（writeBatch 2回） | 2 |
| プロジェクトの削除 | 1 |

合計 **2,130往復**。うち Firestore は **30**（4,200 から）。
Storage の 2,100 は減っていないが、直列から4並列になった。

**つまり律速は Storage の削除に移った。** ここから先を速くするには
同時実行数（`DELETE_CONCURRENCY`、現在 4）を上げるしかない。
どこまで上げられるかは task_006 の実測で決める。

## 実測の手順（未実施）

1. 捨ててよいプロジェクトを新規に作る。**実データで測らない。削除は取り消せない**
2. 写真を50枚アップロードする（700枚で測ると計測自体に十数分かかる）
3. 招待を2件作る
4. ギャラリーで数枚をお気に入りに入れる
5. 開発者ツールのネットワークタブを記録状態にする
6. 削除を実行し、確認ダイアログで「削除」を押してから完了メッセージが出るまでを測る
7. `firestore.googleapis.com` と `firebasestorage.googleapis.com` への往復回数を数える
8. 同時実行数 4 / 8 / 16 でそれぞれ別のプロジェクトを作って測る
9. レート制限のエラーが出ないか確認する。出たら下げる

記録する項目: 枚数・招待数・お気に入り数・回線・ブラウザ・所要時間・往復回数。
**測れなかった項目は「未計測」と書く。推測値を書かない。**
