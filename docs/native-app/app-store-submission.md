# App Store 提出計画（審査通過の確度を最大化する仕様）

作成日: 2026-08-21
対象: `mobile/`（com.nonturn.photogallery / Expo SDK 57 / EAS Build）

## 結論

**「確実に通る」方法は存在しない。** 審査は人間が行い、WebView シェルという構造上、
Guideline 4.2（Minimum Functionality）の裁量リスクはゼロにできない。
ただし、**現状のままでは 4.2 以前に Guideline 2.1（App Completeness）でほぼ確実に落ちる**。
レビュアーがアプリを開くと「招待リンクから開いてください」の行き止まり画面しかなく、
**中身に到達する手段が一切ない**からである（レビュアーは招待リンクを持っていない）。

したがって順序は明確で、
**① レビュアーの入口を作る → ② 4.2 対策と提出物を固める → ③ 提出**、
却下されたら **④ 配布形態のフォールバック** に切り替える。

**入口の実装方式は「招待リンクの貼り付け」に決定した**（2026-08-21）。当初は
ID＋合言葉サインイン（`docs/app-signin/`、15タスク）を想定していたが、審査対策としては
過剰である。既存の `resolveDeepLink` に文字列を渡すだけで達成でき、新しい API も
コレクションも Firestore ルールの変更も要らない。判断の詳細は
`docs/app-store/implementation-plan.md` の Assumption 1 を参照。

## 1. 落ちる要因の分析（このアプリ固有）

| Guideline | 内容 | 現状 | リスク |
|---|---|---|---|
| **2.1** App Completeness | レビュアーが全機能に到達できること | 入口なし（行き止まり画面） | **確実に落ちる。最優先** |

| 5.1.1(v) アカウント削除 | アプリ内でアカウント作成があるなら削除も必須 | アカウント作成なし（ID/合言葉は管理者発行） | **非該当。今後もアプリ内アカウント作成を足さないこと** |

### 4.2 について正直な評価

このアプリのネイティブ固有価値は「**Safari では不可能な、フォトライブラリへの直接保存
（単体＋46枚一括・進捗・キャンセル・追加のみ権限）**」の一点に集約される。
これは本物の機能差だが、画面のほぼ全てが WebView である事実は変わらない。
審査メモで機能差を明示し、体験を「ブラウザではないアプリ」に見せることで確率を上げる。
**それでも却下される可能性は残る**ため、フォールバック（§5）を最初から計画に含める。

## 2. 必須のコード変更（提出前）

### 2.1 招待リンクの貼り付け画面 = レビュアーの入口【最重要・提出のブロッカー】

行き止まりの `NoInvitationScreen` を、招待リンクを貼り付けて開ける画面に置き換える。
**レビュアーの到達経路が二重になる**ことが要点である。

- (a) 審査メモのリンクをタップする → ユニバーサルリンクでアプリが開く（実機確認済み）
- (b) アプリをアイコンから起動し、入力欄にリンクを貼り付ける

**(b) が無いと、アイコンから先に起動されたレビュアーは行き止まりに当たる。**
実装は `docs/app-store/` の task_003。

ID＋合言葉サインイン（`docs/app-signin/`）は、リンクを扱えないクライアント向けの
利便性機能として価値が残るため、審査とは切り離して任意タスク（task_011）に置く。
同計画の前提条件だった「`invitations` の列挙が可能」問題は **2026-08-17 に解消済み**
（list は管理者のみ。実測確認済み）で、着手を妨げるものは無い。

### 2.2 デモ招待が死なない仕様

7日閲覧期限は**3か所**にハードコードされている（当初「2か所」と書いたのは誤り）。
`web/src/services/invitationService.ts`（validateInvitation）、
`web/src/services/manifestService.ts`（isUsable）、
そして `web/src/components/Header.tsx:19`（画面に表示する期限）。
Firestore ルールは `isActive` と `expiresAt` しか見ていないため、**ルール変更は不要**。

- 招待に任意フィールド `viewingDays`（既定 7）を追加し、両関数がそれを読む
- デモ招待は `viewingDays: 3650`・`expiresAt` を遠い将来に設定
- **デモの中身は NonTurn 自身のサンプル撮影**にする。実クライアントの納品写真を
  レビュアーに見せない（プライバシー上も契約上も不可）

### 2.3 審査面を狭める設定変更

- `app.config.ts` の `supportsTablet: true` → **false**。
  iPad 対応を宣言すると iPad 実機での審査と 13インチ iPad スクリーンショットが必須になる。
  iPad では一度も検証しておらず、審査面が広がるだけ。iPhone 専用で出す。
- `ios.infoPlist` に `ITSAppUsesNonExemptEncryption: false` を追加（HTTPS のみ＝適用除外）。
  提出のたびに輸出コンプライアンス質問に答える手作業が消える。

### 2.4 アプリ表示名

`name: 'Photo Gallery'` は汎用的すぎ、App Store 上の名前として通らない可能性が高い
（名前は Store 全体で一意）。候補: **NonTurn Gallery** / ノンターンギャラリー 等。
App Store Connect でアプリレコード作成時に空き確認が必要。

## 4. 審査メモに書く内容（4.2 への反論を先回りする）

1. **用途**: プロカメラマンが撮影写真をクライアントへ納品するための、招待制の閲覧・保存アプリ。
   一般公開のコンテンツは存在しない（だからデモ用の招待を用意した）。
2. **入口（2通り。どちらでも到達できる）**:
   (a) 次のリンクをタップするとアプリが開く: `https://gallery.non-turn.com/gallery/<デモトークン>`
   (b) アプリを起動し、入力欄に同じリンクを貼り付けて「開く」を押す
3. **ネイティブ固有機能（Safari では不可能）**:
   - 写真を端末のフォトライブラリへ**直接**保存（Safari は共有シート経由の1枚ずつのみ）
   - **数十枚の一括保存**、進捗表示、キャンセル
   - 権限は**追加のみ**（`NSPhotoLibraryAddUsageDescription` のみ。読み取り権限を持たない）
   - 招待リンクのユニバーサルリンク起動（gallery.non-turn.com、AASA 設定済み・実機確認済み）
4. サーバー側で招待ごとに認可しており、アプリは URL を直接受け取らない（セキュリティ設計の説明）。

## 5. 却下された場合のフォールバック（決定済みの方針の具体化）

`decisions.md` D2 の「公開ストア第一候補」の下に、段階を1つ足す。

1. **公開 App Store**（第一候補）
2. **Unlisted App Distribution（リンク限定配布）**: 検索に出ず、URL を知る人だけが
   インストールできる。審査は通常どおりだが「限定された対象者向けツール」という文脈が
   付くため、4.2 系の判断が納品ツールの実態と整合しやすい。Apple への申請フォーム1枚。
   **クライアント納品という用途には公開ストアよりむしろ適合する**
3. **TestFlight 外部テスター**（最終フォールバック）: Beta App Review のみ。
   ただし 90 日でビルド失効し、3か月ごとの上げ直しが恒久運用になる（既知のデメリット）

## 6. 実施順序

| # | 作業 | 種別 | 状態 |
|---|---|---|---|
| 1 | 招待リンクの貼り付け画面（`docs/app-store/` task_003） | コード | 計画済み・未着手 |
| 2 | `viewingDays` 対応＋デモ招待作成（自社サンプル写真） | コード＋運用 | 未着手 |
| 3 | `supportsTablet: false`・`ITSAppUsesNonExemptEncryption`・表示名変更 | 設定 | 未着手 |
| 4 | プライバシーポリシーページ作成・公開 | web | 未着手 |
| 5 | App Store Connect レコード作成・スクリーンショット・メタデータ | 提出物 | 未着手 |
| 6 | production プロファイルでビルド → `eas submit` | 提出 | 未着手 |
| 7 | 却下時: §5 のフォールバックへ | 判断 | — |

実行可能な計画は `docs/app-store/`（implementation-plan.md / task-list.json /
acceptance-checks.json、**version 2**）に落としてある。本ファイルは要件調査、あちらが実装手順である。

**2026-08-21 の敵対的レビュー3件（Fable 5 / Codex / Gemini）で、本ファイルと初版の計画に
以下の誤りが見つかったため訂正済みである。**

- 無効なトークンが保存されて**回復不能な行き止まり**になる欠陥を見落としていた（最重要）
- iOS 実機での**保存が未検証**なのに、検証済みであるかのように「回帰」と書いていた
- 閲覧期限を強制境界であるかのように書いていた。**実際は Storage の写真が認証なしで誰でも取得できる**
- デモトークンをリポジトリにコミットする計画になっていた
- `cd admin && npm run lint` を検証コマンドに挙げていたが、**これは何も検査せず終了コード 0 を返す**
- Unlisted App Distribution を 4.2 の回避策のように書いていたが、**審査基準は通常審査と同一**

前提の注意: ローカルのディスク空きが枯渇気味（2026-08-20 時点で 156MB）。
ビルドは EAS のクラウドで行うため提出作業自体は可能だが、web のローカルビルド検証には
`.next` の削除等で空きを作る必要がある（ユーザー判断待ち）。
