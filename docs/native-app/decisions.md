## D1. ゲート 0: Web Share API による代替 — **却下。アプリを作る**

- **判断者**: ユーザー（noritaka）
- **結論**: Web Share API で写真をフォトライブラリへ保存する経路は、技術的に不可能なわけではないが、**求めるユーザビリティを満たさない**。共有シートを経由する手順が煩雑になり、納品先のクライアントに提示できる UX にならない。
- **根拠**: ユーザーが事前に複数の手段を試した結果の実地判断。本セッションでの追加計測は行っていない（未計測であることを明示しておく）。
- **補足（事実の記録のみ、判断を覆すものではない）**: 現行の `web/src/components/ShareButton.tsx` は `navigator.share({ files: [file] })` で **1枚ずつ**共有する実装であり、複数ファイルの同時共有は未実装である。
- **影響**: `task_000` は「却下」で完了扱いとする。ネイティブアプリの実装に進む。

## D2. ゲート 1-a: 配布形態 — **公開ストアを第一候補、TestFlight 外部配布を代替**

- **検討の出発点**: 納品先が「依頼を受けたクライアント」に限られるため、内部配布だけで足りるのではないかという想定があった。
- **その想定を覆した事実**（Apple 公式ドキュメントで確認）:

  | | 内部テスター | 外部テスター |
  |---|---|---|
  | 人数上限 | 100 | 10,000 |
  | App Store Connect アカウント | **必要**（チームメンバーに限る） | 不要（メールまたは公開リンク） |
  | Beta App Review | 不要 | **必要**（グループに追加された時点で自動的に審査へ回る） |

  クライアントはチームメンバーではないため、内部テスターとして招待できない。**クライアントに配る＝外部テスター配布であり、Beta App Review を通る。** したがって「内部配布なら審査を回避できる」という前提は成立しない。

- **もう一つの決定要因**: TestFlight のビルドは**90日で失効する**（App Store Connect ヘルプに「You can test a build for up to 90 days」「Your build becomes unavailable for testers after 90 days」と明記）。TestFlight 運用を選ぶと、3か月ごとに新しいビルドを上げ直す作業が恒久的に発生し、納品期間中のクライアントがアプリを開けなくなるリスクを抱える。

- **結論**:
  1. **第一候補**: App Store / Google Play への公開リリース。審査は一度きりで、90日の失効がない。
  2. **代替**: App Store 4.2（Minimum Functionality）で却下された場合に TestFlight 外部配布へ切り替える。Android は Play の公開リリースで進める（審査は App Store より緩い）。
  3. **最終確定のタイミング**: `task_015`（ストア提出準備と 4.2 の go/no-go 判断）。実機ビルドができてから最終判断する。

- **4.2 への備え**: ネイティブ固有の価値（フォトライブラリへの直接保存・一括保存）を審査メモで明示し、期限切れしないデモ招待を用意する。詳細は `task_015`。

## D3. ゲート 1-b: 配信ドメイン — **独自ドメインを用意する**

- **判断者**: ユーザー（必要なら用意する、との回答）
- **結論**: ユニバーサルリンク / App Links 用に独自ドメインを用意する。`web-kappa-neon-94.vercel.app` のようなプレビュー用ホストのまま進めない。
- **理由**: 招待リンクの https URL からアプリを開くには、`apple-app-site-association` と `assetlinks.json` を安定したドメインから配信する必要がある。ドメインが変わるとリンクが機能しなくなり、既に配布済みの招待リンクが壊れる。
- **確定（2026-08-17）**: **`gallery.non-turn.com`**。`non-turn.com` のゾーンに CNAME を1件
  追加して Vercel に向けた。会社サイト本体とメールには触れていない。
  管理画面が発行する招待リンクもこのドメインに切り替え済み。
  iOS のユニバーサルリンクは実機で動作を確認した（`device-test-log.md` 第5章）。

## D4. 従量課金（モバイルデータ）通信での確認 — **見送り**

- **決定日**: 2026-09-02（監査 `docs/audit-2026-09-02/findings.md` F15 / H1 を受けて）
- **経緯**: 計画（`task-list.json` の task_006）には「セルラー回線での一括保存前に容量を伝えて確認を取る」
  項目があり、その足場として `expo-network` 依存・`MeteredConfirmMessage` 型・`BatchResult.interrupted`
  を先に置いてあった。実装は行われず、web 側にも受け側が無いまま残っていた。
- **結論**: 実装しない。足場も削除する（`expo-network`、`MeteredConfirmMessage`、`BatchResult.interrupted`）。
  - 一括保存を押すのは「ギャラリーを全部保存したい」と決めた利用者で、確認ダイアログを1枚挟む価値が
    通信量の警告に見合わない。
  - 通信量の実効的な歯止めは既にある（件数上限 `MAX_BATCH_ITEMS`、実サイズ合計の上限
    `MAX_TOTAL_BYTES`、空き容量チェック、項目ごとのタイムアウト、キャンセル）。
  - 未使用の型と依存を残すと、web 側が「native はこれを送ってくる」と誤解する余地になる。
    ブリッジの `supports` に `meteredConfirm` を載せたことは一度も無いので、削除で web の挙動は変わらない。
- **`BatchResult.interrupted` について**: バックグラウンド移行の検知（`AppState`）はこのフラグを
  作るためだけに存在し、web は読んでいなかった。フラグと併せて検知も外した。
  「アプリを閉じないでください」の案内は web 側の保存中モーダルが担当する
  （`adversarial-review.md` B1 の採用範囲はそこまで）。
- **再検討する条件**: 実機で「モバイル回線で数百枚を保存して通信量の苦情が出た」事実が観測されたとき。
