# 修正計画: 無効な招待からの回復（app-store の task_003）

作成日: 2026-08-22
方針設計: Fable 5 / 実装計画: Opus 5

## 1. 直す欠陥

ネイティブアプリで、無効な招待に一度当たると**回復不能な行き止まり**になる。
以下はすべてコードと本番に対して実測で確認した事実である。

| # | 事実 |
|---|---|
| 1 | `mobile/App.tsx` の `applyLink` は `resolveDeepLink` が**形式として**解決できた時点でトークンを SecureStore に保存する。招待の有効性は確認しない |
| 2 | 無効な招待でも web は **HTTP 200** を返し `ExpiredLink` を描画する |
| 3 | `ExpiredLink.tsx` にはリンクもボタンも**1つも無い**（grep で0件） |
| 4 | `GalleryWebView` が `hasError` を立てるのは `onError` と `onHttpError >= 500` のときだけ |

**帰結**: トークンを1文字打ち間違えても文字種が合えば保存され、以後アイコン起動のたびに
脱出手段の無いエラーページへ直行し、入口に戻れない。

**現時点の影響範囲**: アプリは未配布（開発機1台のみ）。ブラウザでは
アドレスバーから移動できるため閉じ込めは起きない。**したがって現在の実害は無いが、
配布した後では手遅れ**であり、App Store 提出計画の `task_004`（貼り付け入口＝
Guideline 2.1 対策）はこの修正が成立していることを前提にしている。

**現状でも回復できる唯一の経路**: 撮影者が新しい有効なリンクを送り、利用者がタップすること
（`Linking` リスナー → `applyLink` がトークンを上書きする）。**利用者が自力で脱出できない**点が欠陥である。

## 2. 採用する方針

**web が「確定した無効判定」をネイティブへ通知し、ネイティブが保存済みトークンを破棄する。**

4案（ブリッジ通知 / ネイティブ事前検証 / HTTP ステータス / 常設の脱出口）を比較して決定した。
判断の中心は **web は即時デプロイされ、アプリの更新は審査を挟んで数日〜数週間遅れる**という非対称である。

### 他案を採らない理由

**ネイティブ側で事前検証しない。** `/api/native/manifest` は `imageIds` が空だとトークン評価の前に
400 を返し、ダミーの imageId を送ると有効な招待でも（所属違反で）403 になる。
**既存 API では「この招待は有効か」を問えない。** 新エンドポイントの追加は計画の方針に反する。
加えて、保存時に検証しても翌週期限が切れれば同じ罠に戻るため、毎回の起動時に通信が必要になる。
オフライン起動で fail-open なら罠が復活し、fail-closed なら有効なギャラリーが開けなくなる。

**HTTP ステータスで表現しない。** 有効性の判定は現在クライアント側（匿名認証後の Firestore 読み取り）
にあり、404 を返すには判定をサーバーへ移して有効性ロジックの3つ目の複製を作ることになる。
また、ネイティブ側でメインフレームの 404 とサブリソースの 404 を区別する必要が生じる。
**2026-08-16 に iOS で出た3件の不具合は、すべて WebView の内部挙動への依存が原因**であり、同じ失敗類型になる。

**常設の脱出口を主案にしない。** UI を持たない方針のアプリに常設 UI を足すことになるうえ、
トークンの破棄は結局必要である（破棄しなければ起動のたびにまずエラーページへ着地する）。
ただし考え方は部分的に正しいので、`LoadErrorScreen` に「別の招待を開く」を足す派生を
**`task_004` へ移管する**（この修正には含めない）。

### 採用案の利点

- 無効判定は web が既に行っている場所から発火するため、**判定ロジックの複製がゼロ**
- 発火側が web にあるため、**壊れたときの修正が即時デプロイで届く**（非対称の良い側に乗る）
- ネイティブ側は「トークン破棄して入口へ戻す」という変化しにくい受け皿だけを持つ
- **ブラウザへの副作用が無い**（`postToNative` はシェル外で何もしない）

## 3. 拘束条件（設計の要）

### 拘束条件0: 有効なトークンを、無効な新リンクで失わせない（**Codex の指摘。最重要**）

`applyLink` は **`resolveDeepLink` の形式解決だけで既存のトークンを上書きする**。
つまり有効な招待Aを開いている利用者が、打ち間違えたリンクBを開くと、
**その時点でAが失われる**。破棄処理を足すだけでは「Bを消して入口へ戻す」となり、Aは戻らない。

**セッション中の直前の有効トークンを記憶し、無効通知を受けたらそれに戻す。**
記憶が無ければ破棄して入口へ戻す。これは現状（Aを失ったうえに閉じ込められる）より
確実に良く、コストはメモリ上の1変数である。

### 拘束条件1: 発火点は「表示」ではなく「確定した無効判定」

**初版の計画（`ExpiredLink` の表示時に通知）はこのままでは有効なトークンを誤破棄する。**

`ExpiredLink` は一時的な通信障害でも表示される。実測で確認した経路は2つある。

- `getInvitationByToken` が `getDoc` の**あらゆる例外（オフライン含む）を `null` に握りつぶす**
- `useInvitation` の汎用 catch が同じ `ExpiredLink` に落ちる

表示をトリガーにすると、**電波の悪い場所でアプリを開いただけで有効なトークンが破棄される**。
審査中にレビュアーの回線で起きれば `task_004` の意義そのものを毀損する。

通知してよいのは次の**確定シグナル**に限る。

| シグナル | 意味 | 通知 |
|---|---|---|
| `getDoc` が `permission-denied` | **サーバーが拒否した**（不存在・無効化・期限切れのいずれか） | **する** |
| 取得できたが `validateInvitation` が false、かつ**キャッシュ由来でない** | 閲覧期限切れ | **する** |
| `unavailable` 等の通信系エラー | 一時障害 | **しない** |
| `validateInvitation` が false だが**キャッシュ由来** | 古いデータの可能性 | **しない** |
| その他の例外 | 不明 | **しない** |

**初版の「`getDoc` 成功かつ `!exists()`」という行は誤りだった。** 実測で確認したところ、
存在しない招待も `permission-denied` を返す。ルールが `resource.data.isActive` を評価するため、
ドキュメントが無いと評価に失敗して拒否されるからである。

```
期限切れ招待  → code='permission-denied'
存在しない招待 → code='permission-denied'
```

**これは設計上むしろ好都合である。** 判定が「サーバーが拒否した」か
「サーバーに届かなかった」かの2択になり、列挙対策としても正しい
（クライアントからは不存在と期限切れを区別できない）。

**`validateInvitation` は端末の時刻を使う**（`new Date()`）。端末の時計が数日進んでいると
有効なトークンを誤って破棄しうる。閲覧期限は Firestore ルールが評価しないため
サーバーで確定できない。**キャッシュ由来のスナップショットでは発火しない**ことを条件に加え、
残る時計ずれのリスクは受け入れる。誤検知の代償は「もう一度リンクを入れ直す」ことであり、
**現状の確実な閉じ込めより明確に軽い**。

**副産物として既存の不具合も直る。** 現在は通信障害のときにも
「このリンクは無効か、有効期限が切れています。」と表示されており、事実と異なる。
区別を入れることで、通信障害には「ギャラリーの読み込みに失敗しました。」が出るようになる。

**利用者向けの文言で無効・期限切れ・不存在を撃ち分けてはいけない。** 区別は内部利用のみ。
撃ち分けるとトークンの実在を第三者に伝えることになる（列挙対策の後退）。

### 拘束条件2: nonce が得られるまで送信を保留する（**初版の「再送」は機能しない**）

Android では注入前に送った通知が `nonce: null` となり、ネイティブ側で捨てられる。

**初版は `subscribeToShellReady` での再送を書いていたが、これは動かない。**
この関数は素の `addEventListener` で、**すでに発火したイベントを拾えない**。
無効判定はネットワーク往復の後に出るため、そのときには `native-gallery-ready` が
発火済みである可能性が高く、再送は永遠に呼ばれない。

正しくは、**送信時に `detectNativeShell()?.nonce` を確認する**。
文字列であれば即送信し、`null` であればイベントを待って送る。
ネイティブ側の破棄処理は冪等なので二重送信は無害である。

**nonce の検証は緩めない。** 緩めると第三者の iframe から偽装してトークンを消せる経路ができる。

### 拘束条件3: メッセージに対象トークンを載せ、二重に照合してから破棄する

ペイロードに `token` を1フィールド足し、ネイティブは
**(a) 現在表示中の `sourceUrl` のトークン、(b) 保存中のトークン**の両方と一致した場合のみ破棄する。
「古いページの遅延通知が新しいトークンを消す」可能性を構造的に排除できる。

### 拘束条件4: `BRIDGE_VERSION` を上げない

`parseInboundMessage` は未知の `type` を黙って無視する（コードにコメントで明記されている）。
**受信 type の追加は後方互換であり、バージョンを上げる必要が無い。**
上げると新しい web と古いアプリの間で**全メッセージ**がバージョン不一致で死ぬ。

`SUPPORTED_FEATURES` / `supports` によるゲートも**しない**。応答を要さない一方向の通知であり、
得るものが無い。加えて UA フォールバック検出時の `supports` は web に焼き込まれた定数で、
相手アプリの実能力を反映しないため判定材料として誤っている。

## 5. 実装順序

1. `mobile` のブリッジに受信 type を追加する（先に受け皿を作る。web が先だと通知先が無い）
2. `mobile/App.tsx` の破棄と遷移
3. `web` の `invitationService` に区別を入れる
4. `web` の `useInvitation` で発火
5. テスト
6. **web を本番にデプロイしてから**アプリをビルドする

**デプロイ順序が重要**である。アプリは未配布なので、
「配布されたアプリが存在する時点で web は必ず通知を送る」という状態を初日から作れる。

## 6. 受け入れ基準

1. 無効なトークンを入力した後にアプリを再起動すると、**入口画面に戻る**（エラーページに直行しない）
2. **機内モードで有効な招待を開いても、トークンが破棄されない**（拘束条件1の検証）
3. 通信障害時の文言が「読み込みに失敗しました」になり、「無効か期限切れ」とは出ない
4. 利用者向けの文言が、無効・期限切れ・不存在で**区別されない**
5. ブラウザで無効な招待を開いても例外が出ない
6. 古いアプリが新しい web を読んでも壊れない（未知 type の無視をテストで固定）
7. 別のトークンを対象とする通知では破棄されない
8. 有効な招待を開いた状態から、リンクのタップで別の招待に切り替えられる（回帰）
9. `web` `admin` `mobile` の検証コマンドが既存のベースラインを超えない

### 受け入れるリスク: メッセージは同一ページのスクリプトから偽装できる

nonce は `window.__NATIVE_GALLERY__` として**ページ内のスクリプトから読める**。
同一オリジンのスクリプトが混入すれば `invitationInvalid` を偽装し、
有効なトークンを破棄させられる（レビュー2件が指摘）。

**これは受け入れる。** 理由は3つある。

- 同じ手段で既存の `saveImages` 等も偽装できるため、この修正が新たに開く経路ではない
- 被害は「もう一度リンクを入れ直す」ことであり、情報の漏洩や写真への不正アクセスは生じない
- 拘束条件3の二重照合により、**現在開いている招待以外のトークンは消せない**

nonce は同一ページの JavaScript に対する認証境界ではない、という前提を明記しておく。

## 7. やらないこと

- 新規 API の追加、`/api/native/manifest` の契約変更
- ギャラリールートの SSR 化・HTTP ステータスの変更
- 常設のネイティブ UI（`LoadErrorScreen` の導線は `task_004` へ移管）
- `BRIDGE_VERSION` の繰り上げ、`supports` に基づく送信ゲート
- ハンドシェイク化（応答確認・ack・再試行キュー）。一方向の通知で足りる
- 利用者向け文言での無効・期限切れ・不存在の区別
- 起動時のネットワーク事前検証

## 8. 実機で確認すること（`task_005` のチェックリストに追加する）

Jest は Node 上で走るため、以下は**実機でしか確認できない**。

- 無効なトークン → 再起動 → 入口画面に戻る
- **機内モードで起動 → 有効なトークンが破棄されない**（Android の注入遅延と組み合わせて確認）

## 9. 検証済みになった事項

- **`/liked` は `useInvitation` を使い、同じ `ExpiredLink` に落ちる**（実測で確認）。
  発火を `useInvitation` に置くことで自動的にカバーされる。ページ側には置かない
